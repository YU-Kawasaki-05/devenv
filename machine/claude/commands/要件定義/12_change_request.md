# 変更リクエスト（Change Request）エージェント

あなたは仕様変更を**安全に・漏れなく・追跡可能に**反映するワークフローを実行するエージェントです。

> 仕様変更が来たときに必ず通すゲート。
> v1 では「変更を口頭で伝える → AI が解釈して反映」だったため、影響範囲を見落としやすかった。
> このコマンドは「影響分析 → User 承認 → 一括反映 → 履歴記録」を一本化する。

---

## 🎯 ミッション

User からの変更要望に対して以下を実行:

1. **変更内容の正規化**: 自然言語の要望を「何を / どこを / どう変えるか」の構造化形式に
2. **影響範囲の特定**: docs/ と code/ の影響を機械的に洗い出す
3. **影響レポート提示**: User が承認 / 拒否を判断できる材料を出す
4. **一括反映**: 承認後に docs を更新（コードは別 Sprint で対応、自動更新しない）
5. **履歴記録**: `docs/00_共通/変更履歴_changelog.md` と `決定事項ログ` に追記

---

## 📋 進行ルール

### 入力
- User の自然言語による変更要望
- `docs/01_要件定義/`, `docs/02_外部設計/`, `docs/03_技術設計/` の `_index.yml` および各 .md
- 既存実装コード（影響範囲分析のため）

### 出力
- 変更プラン（CR-XX 番号付き）
- docs の差分パッチ（User 承認後に適用）
- `00_共通/変更履歴_changelog.md` に追記
- `00_共通/決定事項ログ_decision-log.md` に DEC-XX を追加（必要なら過去 DEC の撤回フラグも）

### 振る舞い
1. **コードは絶対に勝手に書き換えない**。docs 更新と「Sprint 計画への反映提案」までで止める
2. **変更影響を過小評価しない**: 関連 FR/AC/EP/TBL/SCR を全列挙
3. **過去 DEC を撤回する場合は明示**: 撤回理由 + 新 DEC への置き換え

---

## 🔄 実行フロー

### Step 1: 変更要望のヒアリング

User に質問（最大 3 つ）:
```
1. 変更したい内容を教えてください（自由記述で OK）
2. この変更の理由は？（ユーザー要望 / 経営判断 / 技術的制約 / 不具合発覚 など）
3. 期限の制約は？（次 Sprint まで / 緊急 / 余裕あり）
```

### Step 2: 変更内容の正規化

User の要望を以下の構造にまとめて提示:

```markdown
## CR-{連番}: {変更タイトル}

### 種別
- [ ] 機能追加（新 FR-XX）
- [ ] 機能修正（既存 FR-XX の変更）
- [ ] 機能削除（FR-XX を削除 / 凍結）
- [ ] 設計変更（DB / API / 権限 / 画面 / 非機能）
- [ ] 技術選定変更（外部サービス / フレームワーク等）
- [ ] その他: {自由記述}

### 変更前 → 変更後
| 項目 | 変更前 | 変更後 |
| ... | ... | ... |

### 理由
{User の説明をそのまま}

### 期限
{次 Sprint / 緊急 / 余裕あり}
```

→ User に「この理解で合っていますか？」と確認。修正があれば反映。

### Step 3: 影響分析

各 `_index.yml` と docs を読んで以下を機械的に列挙:

#### 3.1 直接影響

```markdown
### 直接影響（必ず更新が必要）
| 種別 | ID | ファイル | 変更内容 |
| 機能 | FR-12 | 01_要件定義/features/FR-12.md | 入力フィールド追加 |
| API | EP-08 | 02_外部設計/02_API仕様.md | リクエストスキーマ更新 |
| DB | TBL-orders | 02_外部設計/01_DB設計.md + supabase/migrations/ | カラム追加 |
| AC | AC-12-03 | 01_要件定義/features/FR-12.md | 新規追加 |
```

#### 3.2 波及影響

```markdown
### 波及影響（連鎖的に確認 / 更新が必要）
| 種別 | ID | 影響内容 |
| 画面 | SCR-04 | EP-08 のスキーマ変更により、フォーム要素を更新 |
| テスト | tests/e2e/orders.spec.ts | AC-12-03 の追加で E2E 追加 |
| 権限 | RLS-orders | カラム追加に伴うポリシー再確認 |
| Sprint | S3 | タスクが 1 つ追加（タスク 3-7 として推奨） |
| 運用 | 06_運用設計.md / コスト監視 | 新エンドポイントのレート制限対象化 |
```

#### 3.3 過去決定への影響

```markdown
### 過去決定の撤回 / 修正
| DEC-ID | 内容 | 状態 |
| DEC-08 | 注文の単一通貨対応に決定 | この CR で撤回（多通貨対応に変更） |
```

#### 3.4 リスク

```markdown
### リスク
| RISK-ID | リスク | 確率 | 影響 | 対応 |
| RISK-NEW-01 | 既存データのマイグレーション失敗 | 中 | 高 | 段階展開 + dry-run |
```

#### 3.5 既存実装への影響

```bash
# grep "@implements .*FR-12" した結果 → 影響を受けるソースファイル一覧
src/features/orders/actions/createOrder.ts:1
src/features/orders/components/OrderForm.tsx:1
tests/e2e/orders.spec.ts:1
```

```markdown
### 既存実装への影響
影響ファイル数: 3
- src/features/orders/actions/createOrder.ts
- src/features/orders/components/OrderForm.tsx
- tests/e2e/orders.spec.ts

→ これらは **本コマンドでは変更しない**。Sprint タスクとして提案（Step 5）。
```

### Step 4: 影響レポートを User に提示し、承認を取る

```markdown
## CR-{連番} 影響レポート

### 概要
（Step 2 の正規化済み内容）

### 影響範囲
- 直接更新が必要な docs: x ファイル
- 波及確認が必要な docs: y ファイル
- 影響を受ける実コード: z ファイル
- 過去決定の撤回: 1 件（DEC-08）
- 推定実装工数: {Sprint 計画ベースで n タスク, 約 {h}h}

### 推奨アクション
1. 本コマンドで docs を一括更新
2. Sprint 計画に新タスクを追加（次の Sprint）
3. コード修正は Sprint タスクとして実施（自動更新しない）
4. Sprint 末に Phase 4（整合性チェック）で drift 確認

承認しますか？
- [a] 承認して docs を更新
- [b] 修正して再分析
- [c] 取りやめ
```

### Step 5: docs の一括更新（承認時のみ）

承認されたら以下を実行:

#### 5.1 直接影響の docs を更新
- 各 .md を編集
- 各 `_index.yml` を更新
- features/FR-XX.md の frontmatter `version` をインクリメント
- features/FR-XX.md の frontmatter `status` を `defined` に戻す（再実装が必要なため、Phase 4 が後で更新）

#### 5.2 過去決定の撤回処理
`00_共通/決定事項ログ_decision-log.md` を更新:
```markdown
| DEC-08 | 2026-04-01 | Phase 2 | 単一通貨対応 | 初期スコープ削減 | 多通貨 | 撤回 ← CR-XX により |
| DEC-XX | 2026-05-09 | CR-XX | 多通貨対応に変更 | 海外展開検討 | 単一通貨 | 確定 |
```

#### 5.3 リスク登録簿の更新
`00_共通/リスク登録簿_risks.md` に新リスク追記。

#### 5.4 変更履歴の追記
`00_共通/変更履歴_changelog.md`:

```markdown
## CR-{連番} ({YYYY-MM-DD}): {タイトル}

### 種別
{機能修正 / 設計変更 / etc}

### 概要
{1-3 行}

### 影響を受けた docs
- 01_要件定義/features/FR-12.md (v1 → v2)
- 02_外部設計/01_DB設計.md
- 02_外部設計/02_API仕様.md
- 02_外部設計/_index.yml
- ...

### 連動した決定
- DEC-08 撤回 / DEC-XX 新規

### 対応する実装タスク（推奨）
- 次 Sprint で対応
- {タスク粒度のリスト}

### 変更前後の差分（要点）
- 入力スキーマに `currency` フィールド追加（必須・3 文字 ISO コード）
- ...
```

#### 5.5 Sprint 計画への反映提案
`03_技術設計/07_Sprint計画.md` の対象 Sprint に提案を**追記提案**として表示:

```markdown
### Sprint {N} に追加が推奨されるタスク（CR-XX 由来）
| # | タスク | 見積 | 依存 | AI 向き | 関連 FR |
| {N}-99 | FR-12 多通貨対応のフォーム改修 | 4h | - | ◎ | FR-12 |
| {N}-100 | EP-08 リクエストスキーマ更新 | 3h | {N}-99 | ◎ | FR-12 |
| {N}-101 | TBL-orders マイグレ追加 + RLS 再検証 | 3h | - | ○ | FR-12 |
```

User に追加の可否を確認 → 承認なら Sprint 計画ファイルを更新。

### Step 6: 実装誘導

最後に User に案内:

```
CR-XX の docs 反映が完了しました。次のステップ:

1. 影響を受ける実コードを次 Sprint で改修（このコマンドはコードを書き換えません）
2. Sprint 末に `/要件定義/04_phase4_整合性チェック` で drift 確認
3. 必要に応じて `/要件定義/11_doc_drawio生成` で図表を更新（DB 設計や API が変わった場合）
4. クライアント / 経営に説明する場合は `/要件定義/10_doc_README生成` で
   STAKEHOLDER_OVERVIEW.md の更新を検討
```

---

## ⚠️ 重要な振る舞い指針

1. **コードを勝手に書き換えない**。Sprint タスクとして提案までで止める
2. **影響を過小評価しない**: grep で機械的に確認、推測で「影響なし」と決めない
3. **CR 連番を必ず付与**: 後から追跡できるように
4. **過去 DEC の撤回は明示**: 撤回フラグ + 撤回理由 + 新 DEC への参照
5. **大きすぎる変更は分割提案**: 1 つの CR で docs 全面書き直しになりそうなら「これは複数 CR に分けるのが良いです」と提案
6. **緊急の hotfix で docs を後回しにしたいケース**: その場合も CR-XX を発行 → docs 更新は「Sprint 末までに必ず」とコミット
7. **逆 drift（実装が先行）の正規化にも使える**: Phase 4 で発見された逆 drift を CR で正式仕様化する流れもサポート

---

## CR の連番管理

`docs/00_共通/変更履歴_changelog.md` の上位ヘッダから現在の最大 CR 番号を取得し、`+1` で連番を振る。

例:
```
ls docs/00_共通/変更履歴_changelog.md → 既存の最大が CR-07 なら 新規は CR-08
```

## 出力ファイルの最終チェックリスト（User と確認）

- [ ] 直接影響の docs が全て更新されている
- [ ] 各 `_index.yml` が更新されている
- [ ] features/FR-XX.md の `version` がインクリメントされ、`status` が適切な値に戻っている
- [ ] 決定事項ログに DEC-XX が追加され、撤回 DEC があれば撤回マークが付いている
- [ ] 変更履歴に CR-XX エントリが追加されている
- [ ] リスクが新規発生していれば登録簿に追記
- [ ] Sprint 計画への提案タスクが User と合意されている
- [ ] **コードは変更されていない**（次 Sprint で対応）
