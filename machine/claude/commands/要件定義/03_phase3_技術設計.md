## 📋 進行ルール

### 絶対遵守
1. **Phase 1-2 の全成果物（`_index.yml` 含む）を読み込む**
2. **一度に聞く質問は最大 3 つ**
3. **技術選定は必ず複数案を比較表で提示** → User が選ぶ
4. **「なぜそれを推奨するか」の理由を必ず添える**
5. **User の技術レベル・チーム構成を考慮**
6. **各フェーズの成果物をファイル出力 → User 確認**
7. **`[推測]` `[仮決定]` タグを使い分け**
8. **「やりすぎ設計」を避ける**。プロジェクト規模に適切な複雑さ
9. **用語集・決定事項ログ・リスク登録簿を継続メンテ**

### 対話スタイル
- 技術選定は **比較表（メリット/デメリット/コスト/学習コスト）** を必ず提示
- User の経験技術を尊重しつつ、より良い選択肢があれば提案
- 具体的な config 例・ディレクトリ例で認識合わせ

```markdown
# ディレクトリ構成

\`\`\`
project-root/

├── src/

## 2. 設計思想: features 単位の機能凝集
**原則: 「この機能を消したい」ときにフォルダごと消せる構造**

1. その機能でしか使わない → `features/{name}/`
2. 2 つ以上の機能で使う → `shared/` に昇格

| テスト | *.test.ts | sendMessage.test.ts |

## 4. インポートルール
- パスエイリアス: @features/* @shared/*
- features 間の直接 import 禁止（必ず index.ts 経由）
- バレルエクスポートは index.ts と shared/components/ui のみ
```

### PHASE 5: 開発ガイドライン

**目的**: チーム開発で統一的なコード品質を保つルール。
**成果物**: `03_技術設計/05_開発ガイドライン.md`

#### v2 重要追加: ファイル冒頭コメントに `@implements` タグを必須化

```markdown
# 開発ガイドライン

## 1. 環境構築手順
（README.md にも記載）

## 2. Git 運用
- ブランチ戦略: GitHub Flow
- ブランチ命名: feature/{issue}-{topic}
- コミット: Conventional Commits
- PR: テンプレート使用、レビュー 1 人以上必須

## 3. コーディング規約
- TypeScript strict mode 必須
- any 型禁止（unknown + 型ガード）
- 関数の戻り値型は明示
- マジックナンバー禁止（定数化）
- エラーは Error 型 / カスタムエラーで throw
- 1 コンポーネント = 1 責務、100 行超は分割検討

## 4. AI 生成コード規約 ★ v2 強化

### 4.1 ファイル冒頭コメント（必須）
全ファイルの冒頭に以下を付与:

\`\`\`ts
/** @file
 * 機能: {1 行要約}
 * 入力: {引数・FormData の型と形式}
 * 出力: {戻り値の型と形式}
 * 例外: {エラーと HTTP ステータス}
 * 依存: {環境変数・import モジュール}
 * 副作用: {DB / 外部 API / メール}
 * セキュリティ: {ID 検証・RLS・Service Role の扱い}
 * @implements FR-01, AC-01-01, AC-01-02
 */
\`\`\`

**`@implements` タグは必須**。Phase 4（整合性チェック）が機械的に逆引きする根拠になる。
- 該当する FR-XX、AC-XX-XX を全て列挙する
- リファクタで対象が変わったら更新する
- 該当なしの shared/utility は `@implements -` と明記

### 4.2 テストファイルの規約
\`\`\`ts
/** @file
 * 検証: {何をテストするか}
 * @verifies AC-01-01, AC-01-02
 */
\`\`\`

### 4.3 AI 生成コードの必須チェック
- [ ] 入出力の型が明示されているか
- [ ] エラーハンドリングが網羅されているか
- [ ] 環境変数の存在チェックがあるか
- [ ] ユーザー ID の出所が検証されているか
- [ ] Service Role キーがクライアントに露出していないか
- [ ] テストが同時に生成されているか
- [ ] **@implements タグが付与されているか**

## 5. コンポーネント設計
- Server Components デフォルト、Client は最小化
- "use client" はツリー末端
- Presentational / Container 分離
- Props 型は同ファイルで type 定義 + export

## 6. エラーハンドリング

### 統一エラー型
\`\`\`ts
type AppError = {
  code: string
  message: string
  status: number
  details?: unknown
}
\`\`\`

### レイヤー別責務
- Server Actions: try-catch + AppError 返却
- API Routes: 統一エラー JSON + ステータス
- Client: ErrorBoundary + error.tsx + Toast 通知
- ログ: Sentry に自動送信（>= 500 のみアラート）

## 7. テスト規約
（Phase 2 の `06_テスト戦略.md` に従う。ここでは抜粋）
- ユニット: ビジネスロジック・ユーティリティは必須
- 統合: Server Actions は必須
- E2E: 主要フロー必須
- 配置: 対象ファイルと同階層に *.test.ts

## 8. PR テンプレート

\`\`\`md
## 概要
## 変更内容
## スクリーンショット / 動画
## テスト結果
- [ ] pnpm test 通過
- [ ] pnpm typecheck 通過
- [ ] pnpm lint 通過
## 影響範囲
- RLS 影響 / コスト影響 / UX 影響
## レビュー観点
- [ ] RLS が破壊されていないか
- [ ] コスト暴走リスク
- [ ] UX 劣化
- [ ] テスト追加
- [ ] @implements タグの整合性
\`\`\`

## 9. ESLint / Prettier
（具体的設定）

## 10. CI/CD パイプライン
\`\`\`mermaid
graph LR
  A[Push/PR] --> B[Lint + 型]
  B --> C[Unit + Integration]
  C --> D[Build]
  D --> E{PR?}
  E -->|Yes| F[E2E smoke]
  F --> G[Preview Deploy]
  G --> H{main?}
  H -->|Yes| I[Prod Deploy]
\`\`\`
```

### PHASE 6: 運用設計（Observability & Operability）★ v2 新規

**目的**: ローンチ後の観測・運用に必要な設計を初版から織り込む。
**成果物**: `03_技術設計/06_運用設計.md`

#### 進め方

**Step 6-1: ログ設計**
- 何を / どの形式 / どこに
- 個人情報のマスキング方針

**Step 6-2: メトリクス・アラート**
- 監視サービス（Sentry / Datadog / Vercel Analytics）
- アラート閾値と通知先

**Step 6-3: コスト監視 ★ 重要**
特に LLM・外部 API。**閾値で自動停止する仕組み** まで設計する。
ここを軽視するとプロダクションでコスト爆発が起きやすい。

**Step 6-4: バックアップ・リストア**
- DB スナップショット頻度
- 試験リストア手順

**Step 6-5: インシデント対応 runbook**
よくある障害（DB ダウン・外部 API 障害・コスト暴走）に対する初動手順

#### 出力フォーマット

```markdown
# 運用設計

## 1. ログ設計
### 1.1 出力先
- アプリケーションログ: 標準出力 → Vercel ログ → BigQuery（保管 90 日）
- エラーログ: Sentry
- 監査ログ: 専用テーブル（auth.audit_logs）

### 1.2 ログレベル方針
| レベル | 用途 | 例 |
| ERROR | 復旧不可・即対応 | 外部 API 完全失敗 |
| WARN | 復旧可能・要確認 | リトライで成功 |
| INFO | 主要イベント | ログイン成功 |
| DEBUG | 開発時のみ | 内部状態 |

### 1.3 構造化ログフォーマット
\`\`\`json
{
  "timestamp": "...",
  "level": "ERROR",
  "user_id": "...",     // ハッシュ化 or 削除
  "request_id": "...",
  "feature": "FR-XX",
  "message": "...",
  "error": { "code": "...", "stack": "..." }
}
\`\`\`

### 1.4 個人情報マスキング
- メール: 末尾 4 文字以外をマスク
- 電話 / 住所: ログに出さない
- 認証トークン: 絶対に出さない

## 2. メトリクス・アラート

### 2.1 計測指標
| 指標 | ツール | 閾値 | アラート先 |
| エラーレート | Sentry | > 1% / 5min | Slack #alerts |
| p95 レイテンシ | Vercel | > 1s / 5min | Slack #alerts |
| 5xx 率 | Vercel | > 0.5% / 5min | PagerDuty |

### 2.2 ビジネスメトリクス
| 指標 | 元 | 集計 | ダッシュボード |
| DAU | auth.users login | 日次 | Metabase |
| 主要機能の利用率 | events table | 日次 | Metabase |

## 3. コスト監視 ★

### 3.1 監視対象
| サービス | 月予算 | 警告閾値 | 停止閾値 | 停止方法 |
| OpenAI API | $300 | $200 | $280 | 環境変数 ENABLE_AI=false で機能無効化 |
| Vercel | $20 | $15 | - | プラン変更検討 |
| Supabase | $25 | $20 | - | プラン変更検討 |

### 3.2 自動停止の仕組み
- 日次バッチで使用量を計測 → 閾値超過で `kill_switch` テーブルを更新
- アプリ起動時 / 機能呼び出し時に kill_switch を確認 → 該当機能を停止
- Slack 通知 → 担当者が原因調査

### 3.3 暴走防止のレート制限
- ユーザーあたり: 100 req/min（API 全体）
- LLM 呼び出し: 10 req/min/user, 月 100 リクエスト/user
- 大量トークン生成: max_tokens 必ず指定

## 4. バックアップ・リストア
| 対象 | 頻度 | 保管期間 | リストア手順 |
| DB | 日次（自動） | 30 日 | docs に手順 |
| Storage | 週次 | 90 日 | docs に手順 |

**試験リストア**: 四半期に 1 回、テスト環境で実施。

## 5. インシデント対応 runbook

### 5.1 初動共通
1. Slack #incidents で「インシデント宣言」
2. 影響範囲の確認（何機能 / 何ユーザー）
3. ステータスページ更新（必要なら）
4. 暫定対応 → 恒久対応

### 5.2 シナリオ別

#### S-01: DB ダウン
- 検知: Supabase 監視 + Sentry エラー急増
- 初動: Supabase ステータス確認 → ベンダー依存ならステータスページ案内
- 復旧後: 失敗したリクエストの再実行可否を確認

#### S-02: 外部 API（OpenAI 等）障害
- 検知: 該当機能のエラーレート急増
- 初動: kill_switch でその機能を停止 + 代替メッセージ表示
- 復旧後: kill_switch 解除

#### S-03: コスト暴走
- 検知: 日次コストアラート
- 初動: 該当機能停止 → 原因調査（バグ / 攻撃 / 想定通りの利用増）
- 恒久: レート制限見直し / 課金 UI 追加

## 6. 運用ドキュメントの所在
- `docs/runbooks/` に各シナリオの手順
- ステータスページ: {URL}
- オンコールローテーション: {URL}
```

## ⚠️ 重要な振る舞い指針

1. **Phase 1-2 を必ず全部読む**
2. **技術選定は比較表必須**。「これが良い」だけで終わらせない
3. **チーム規模・経験に合わせる**。2 人チームにマイクロサービス提案しない
4. **「やりすぎ設計」を避ける**（YAGNI）
5. **具体的なコード・config 例を多用**
6. **仮決定を残さず確定**させる
7. **完了時、全 P0 機能が「アーキ・ディレクトリ・サービス・認証・Sprint・テスト」全レイヤーでカバーされている整合性表を作成**
8. **Sprint 計画では全 P0 がいずれかの Sprint に配置されていることを検証**
9. **AI 指示テンプレートは User の実際の AI 利用方法を確認してからカスタマイズ**

## 🛡️ 技術設計の品質ルール

### ディレクトリ構成
- features 単位の機能凝集を基本
- shared への配置は「2 箇所以上で使う」確認後
- 「将来使うかも」で shared に置かない

### AI 生成コード規約の位置づけ
- **`@implements FR-XX, AC-XX-XX` タグを強制**（Phase 4 が drift を検出する根拠）
- ファイル冒頭コメント（入出力・例外・依存・副作用・セキュリティ）を強制
- AI 生成コードのチェックリストを PR レビューに組み込む

### セキュリティ設計の最低基準
- CSP ヘッダー
- HSTS / X-Frame-Options 等
- Service Role はサーバーサイド限定
- 認証エンドポイントのレート制限
- ユーザー ID は JWT → auth.uid()、クライアント送信値を信用しない

### 運用設計の最低基準
- ログ・メトリクス・アラート
- コスト監視と自動停止
- バックアップ・試験リストア
- runbook
（これら全てが揃わない限りローンチ準備完了としない）
