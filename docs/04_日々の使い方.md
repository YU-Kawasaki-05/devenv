# A. エージェントに仕事を頼む

> 共通: 担当プロジェクトのディレクトリで `claude` を起動 → スラッシュコマンドで Skill を呼ぶ

## A1. PR / 差分のレビューをお願いしたい
```
/pr-review
```
現在のブランチの差分を、対応漏れ・テスト不足・セキュリティの観点で見てくれます。

## A2. テストが落ちた、エラーログを調べたい
```
/debug-investigator
```
失敗したテストやスタックトレースを渡すと、原因の切り分けと再現手順をまとめてくれます。

## A3. テストを追加してほしい
```
/test-specialist
```
カバレッジ漏れやエッジケースを補完するテストを追加してくれます。**プロダクトコードは触らない**よう設定済み。

## A4. スライドを作りたい

**受け手が PowerPoint で編集する場合** → `slide-gen` (PPTX 出力)
```
/slide-gen
```
内容を伝えると `~/develop/slide-gen/` の生成キットを使って `.pptx` を生成します。座標を直接いじらず、決まったレイアウトで安定生成。

**提案書・対外資料など、見栄え重視で読まれるだけの場合** → `slide-web` (HTML / PDF 出力)
```
/slide-web
```
`~/develop/slide-web/` の Slidev キットを使い、アニメーション付きの HTML スライドと PDF を生成します。ブラウザで即プレビュー、URL で共有可能。
どちらを使うか迷ったら → 受け手が「編集する人」なら slide-gen、「読む人」なら slide-web。

両スライドキットは `slide-kit` profile (devenv 管理) で共通ルールを共有しています。

## A5. ライブラリのバージョンを上げたい
```
/dependency-upgrade
```
Next.js / Rails / TypeScript など、フレームワーク・ランタイム・パッケージマネージャの更新を支援。互換性チェックも行う。

## A6. 設計判断を記録したい (ADR)
```
/adr-writer
```
「なぜこの技術を選んだか」を Architecture Decision Record として残します。

## A7. UI のアクセシビリティをチェックしたい
```
/a11y-review
```
キーボード操作・フォーカス挙動・ARIA 属性・WCAG 準拠などを確認してくれます。

## A8. リリース準備したい
```
/release-manager
```
チェンジログ、バージョンバンプ、デプロイチェックリスト、ロールバック計画などを作成。

# B. 環境を整える / 配布する

## B1. 担当プロジェクトの正本セットを最新化する

毎日 / 週 1 回くらいの頻度で実行する習慣にすると drift しません。

```bash
cd ~/develop/devenv
git pull origin main                                       # 正本リポジトリを最新化
./scripts/diff.sh ~/develop/<自分のプロジェクト> --names-only   # 差分確認
./scripts/sync.sh ~/develop/<自分のプロジェクト> --dry-run     # 何が変わるか確認
./scripts/sync.sh ~/develop/<自分のプロジェクト>               # 反映
```

## B2. 新しいプロジェクトを管理対象に追加する

1. プロジェクトを `~/develop/` に clone
2. `~/develop/devenv/manifest.yml` に追加:
   ```yaml
   projects:
     ...既存...
     <新プロジェクト名>: docs-first-web   # profile を指定
   ```
   利用可能な profile:
   - `docs-first-web` — 通常の Web / アプリ系プロジェクト
   - `slide-kit` — スライド生成系 (slide-gen / slide-web)
3. dry-run で確認:
   ```bash
   cd ~/develop/devenv
   ./scripts/sync.sh ~/develop/<新プロジェクト名> --dry-run
   ```
4. 既存 CLAUDE.md などと衝突しなければ実 sync:
   ```bash
   ./scripts/sync.sh ~/develop/<新プロジェクト名>
   ```
5. devenv をコミット:
   ```bash
   cd ~/develop/devenv
   git add manifest.yml
   git commit -m "manifest: add <project name>"
   ```

## B3. プロジェクト固有の上書き (override) を追加する

「このプロジェクトだけ CLAUDE.md を別物にしたい」「このプロジェクトだけ verify.sh を変えたい」という場合。

```bash
cd ~/develop/devenv
mkdir -p overrides/<プロジェクト名>
# 例: CLAUDE.md だけ固有版を持つ
cp ~/develop/<プロジェクト名>/CLAUDE.md overrides/<プロジェクト名>/CLAUDE.md
# 編集はこちらの override 側で行う
```

dry-run で挙動確認 → 問題なければコミット:
```bash
./scripts/sync.sh ~/develop/<プロジェクト名> --dry-run
git add overrides/
git commit -m "overrides: add <project name>-specific files"
```

## B4. 正本を編集して全プロジェクトに反映する

例えば「全プロジェクトの PR レビュー Skill のチェック項目を追加したい」場合。

```bash
cd ~/develop/devenv

# 1. 正本を編集
code templates/docs-first-web/.agents/skills/pr-review/SKILL.md

# 2. devenv 内で履歴を残す
git add templates/
git commit -m "pr-review: add accessibility checklist item"

# 3. 各プロジェクトに dry-run で確認
./scripts/sync.sh ~/develop/Ardors-website --dry-run
./scripts/sync.sh ~/develop/schedule_app --dry-run
./scripts/sync.sh ~/develop/lifeapp --dry-run

# 4. 問題なければ反映 (各プロジェクト)
./scripts/sync.sh ~/develop/Ardors-website
./scripts/sync.sh ~/develop/schedule_app
./scripts/sync.sh ~/develop/lifeapp
```

## B5. 新しい Skill を追加する

### グローバル (個人用) Skill
個人がどのプロジェクトでも使えるもの。`~/.claude/skills/<skill 名>/SKILL.md` を作成。

```bash
mkdir -p ~/.claude/skills/my-new-skill
code ~/.claude/skills/my-new-skill/SKILL.md
```

`SKILL.md` の冒頭は frontmatter で書く:
```markdown
---
name: my-new-skill
description: Use when ... (どんな時に呼ばれるべきか)。Do not use for ... (使わないケース)。
---

# My New Skill

## Goal
... (この Skill の目的)

## Workflow
1. ...
2. ...

## Output
- ...
```

Codex でも同じ Skill を使うなら symlink を張る:
```bash
ln -s ~/.claude/skills/my-new-skill ~/.agents/skills/my-new-skill
```

### プロジェクト共通 Skill (チームで使う)
`~/develop/devenv/templates/docs-first-web/.agents/skills/<skill 名>/` に配置 → 各プロジェクトに sync で配布。

```bash
cd ~/develop/devenv
mkdir -p templates/docs-first-web/.agents/skills/my-team-skill
code templates/docs-first-web/.agents/skills/my-team-skill/SKILL.md
# (frontmatter + 本文を書く)

git add templates/
git commit -m "skill: add my-team-skill"

# 各プロジェクトに dry-run → 反映
./scripts/sync.sh ~/develop/Ardors-website --dry-run
./scripts/sync.sh ~/develop/Ardors-website
```

# C. 確認・調査

## C1. 自分のプロジェクトと正本の差分を確認したい
```bash
cd ~/develop/devenv
./scripts/diff.sh ~/develop/<プロジェクト> --names-only   # 変更ファイル名のみ
./scripts/diff.sh ~/develop/<プロジェクト>                 # 全文 diff
```

## C2. どのプロジェクトが管理対象か知りたい
```bash
cat ~/develop/devenv/manifest.yml
```

`pending` や `out of scope` のコメント行も合わせて読むと、なぜ載っていない / 載っているかが分かります。

## C3. ある Skill が何をしてくれるか知りたい
```bash
# Claude Code を起動して
claude
# プロンプトに / を打つと一覧が出る
# 詳細は SKILL.md を直接読む
cat ~/.claude/skills/pr-review/SKILL.md
cat ~/develop/<プロジェクト>/.agents/skills/pr-review/SKILL.md
```

# よくある運用パターン

### 朝の儀式 (推奨)
1. `cd ~/develop/devenv && git pull` で正本を最新化
2. `./scripts/diff.sh ~/develop/<自分のプロジェクト> --names-only` で差分確認
3. 差分があれば dry-run → sync で反映
4. その日の仕事を始める

これで「気づかぬうちに古い指示書で動いていた」事故を防げます。

### 金曜の片付け (推奨)
1. その週に変えた正本があれば commit してチームに push
2. 次の週、各人が朝の儀式で取り込む
